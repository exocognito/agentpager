# AgentPager

## Vision

AgentPager makes it easy for me to leave my agents working on my computer or in a cloud VM and send owner decisions to my phone so they can continue to do useful work while I am away.

## Strategic capabilities

### SC1 · Unblock my agent from my phone

Connect my agent to my phone easily: the agent gives me a QR code or a link, or I copy a link from my phone to give the agent. To pair, the agent sends me a decision with five random emoji and tells me which one to choose.

Once paired, my agent sends me a multiple-choice decision when it needs me. I answer, see that my answer was sent, and get the agent's acknowledgement and its next steps. I can look back at past decisions.

Decision cards can show the exact email, pull request, calendar invitation or reply, the way that product would show it, with the agent's options for what to do with it. The agent carries out the option I chose; AgentPager only carries my answer.

Accounts should let me return across devices without making a guest session public.

<!-- Learn whether owners value longer sessions before building subscriptions. -->

## Strategic invariants

### SI1 · Sending a decision requires confirmation

Following good UX practice, an action that cannot be undone needs a confirming step. So an answer always takes two taps: I choose an option or write a response, then press Send. Choosing alone never sends. The agent receives exactly what I sent.

### SI2 · Only the first phone gets in

The first phone to claim a pairing link reserves the session; later devices are refused, and the first keeps it. Choosing the emoji the agent showed and pressing Send pairs it; a wrong choice leaves it unpaired. Pairing links are unguessable and work once. A lost phone means a new session, never a transfer.

### SI3 · Sent decisions cannot be changed

I can reread the question, my answer and the agent's acknowledgement, but not change them.

### SI4 · An acknowledgement always comes from the agent

An acknowledgement is a real message from the agent, never an automatic message from AgentPager. The phone tells apart "your answer was sent" from "your agent received it".

### SI5 · A free session ends when I end it, or 24 hours after pairing

When my agent finishes, I can still read the session until it ends. Once a session ends or expires, its decisions are deleted.

### SI6 · UTF-8 with Markdown is allowed; invalid or over-limit text is refused, never truncated

Card titles, option labels, option detail and agent acknowledgements allow 280 visible characters; question detail and my written feedback allow 1,000. Count spaces and Markdown punctuation. Text is valid UTF-8 with Markdown and no HTML. Anything else is refused whole, with an error that tells the agent what to fix. Nothing is truncated or silently cleaned. On screen, titles, option labels and session names show each run of spaces and line breaks as one space; detail text shows them as sent.

### SI7 · Cards are independent

Several cards can be open at once and answered in any order. Answering one never changes another.

### SI8 · Approval refers to the exact proposal

Before I answer a rich card, I see its complete target and content, and my answer refers to exactly that version.

### SI9 · Research never pretends to be an available paid upgrade

A Pro research offer takes no payment and changes nothing about my sessions. It sends my feedback only with my consent.

## Strategic goals

### SG1 · Return to completed work, not an unseen question

I can walk away while my agent works and come back to finished work, not a question I never saw. Later, measure the stops prevented and the time or tokens unblocked.

### SG2 · Agents use a helpline instead of bad decisions

An agent that is blocked or unsure about a risky step asks me for a quick go/no-go instead of stopping or taking the risk. Later, measure fewer bad decisions and unnecessary stops.

### SG3 · Learn which paid value can sustain the product

Test whether owners need longer-running agents, for which work, and whether $2.99 a month fits that value. Clicks and surveys show interest, not revenue.

## Strategic principles

### SP1 · Make the usual answer easy and clear

Use plain language I can understand without specialist knowledge. Always offer feedback, except on the pairing card, for when the options do not fit; feedback is the fallback, not the usual path.

### SP2 · Keep the first version focused and its foundations explicit

Serve one agent and one phone per session. Accounts, native apps, community cards and paid plans need their own design and user learning. Run on a Cloudflare Worker at agentpager.me, with one SQLite-backed Durable Object per session. Agents reach one service by plain HTTPS or a remote MCP server. Defer Alchemy until a date the owner sets.

### SP3 · Agents choose the options; AgentPager keeps them easy to answer

For every card, the agent chooses the question, two to five options and their emoji. Each option is one target, its emoji and title, with no radio, check or number. The emoji tells options apart, so I can refer to them in feedback, such as "do 🚀 and then 🛠️". I choose one option, never several. On a product card the options are the actions the agent offers, such as Send now or Send tomorrow.

### SP4 · Keep the decision short; make detail optional

Aim for about 100 characters for the question and for each option. The agent may name the option it recommends; it shows under the question, with the question's detail as a short reason, never a second question. Nothing is chosen for me. Each option may carry about 200 characters of detail, shown only while it is chosen. These are writing guides; SI6 sets the hard limits.

### SP5 · Reach the agents owners actually use

Any agent whose client can send HTTPS requests or add an MCP server can use AgentPager from agentpager.me/start alone, with nothing to install. That covers terminal agents, desktop and IDE apps, and chat apps on my phone. /start is written for developers of every level. A waiting agent has my answer within a second of the Undo window closing.

# MHELPER · Optional helper for several agents and answer delivery

## Objective

I can give an agent the remote AgentPager MCP server and use the complete pairing, decision, feedback, answer, acknowledgement and history flow without installing a helper. When I choose to install one helper on my laptop or a spike VM, it helps connect several supported agent clients there, keeps their sessions separate, shows their connection and activity state on my phone, and brings my answer back to the agent that asked even after its turn has gone idle. My phone cannot start a new task, send an arbitrary instruction, restart a process or grant tool permissions.

One installation configures supported clients; it is not one shared agent identity. Every agent session still pairs with its own phone authorization and remains independently endable. The same phone browser can hold those sessions through the existing home screen. An installed client is not claimed to be supported until its named setup, answer delivery and status capabilities have been qualified.

## Out of scope

1. Arbitrary phone instructions, model-generated status requests, remote shell, process launch/restart, permission approvals and changing an agent's execution policy.
2. Native phone apps, background notifications, replacing the browser polling transport, accounts, device recovery, shared machine-wide pairing and merging agents into one decision queue.
3. Universal client support, auto-installing agent clients or authenticating them for the owner, configuring other machines over SSH, and claiming a helper installed on one machine controls an unrelated backend elsewhere.
4. End-to-end confidentiality or a claim that a compromised relay cannot forge owner messages. The trust choice must be explicitly accepted or replaced before activation; the current relay-readable design is not silently renamed secure against relay compromise.
5. A required Bun implementation, a particular packaging tool, a WebSocket rewrite or any new protocol chosen only for its own sake.

## Entry and approval gates

1. MCARDS is the predecessor. Its still-applicable promises remain regression obligations; MHELPER does not close it or imply its implementation exists.
2. The owner reviews the statements and their required items, the proposed host/client scope and thresholds, and the activation amendments in the proposal record.
3. Host integrations are qualified against actual client APIs. A client that cannot report activity or accept bounded answer delivery remains unsupported for that capability; no transcript guessing substitutes for an event interface.
4. Schemas, state machines, effects/routes, screens and verification are completed and approved at one exact cumulative revision. Draft prose and the HTML proposal are not that executable design or formal proof.
5. Only after those gates, with all selected promises active, is the full deliverables block added and status changed to active. No helper build, deployment or driver launch is authorized by this proposal.

# Terms

The words that mean something specific in this product. They name things; the promises and schemas say how the things behave.

| Term | Meaning |
| --- | --- |
| Owner | The person an agent works for, answering on their phone. |
| Agent | The AI program that asks. It reaches the service over HTTPS or MCP. |
| Start page | The one page at `/start` that tells an agent everything it needs. |
| Session | One agent and one phone, paired, exchanging cards until it ends or expires. |
| Finished | The agent is done with a session: it can ask nothing more, and the owner can still read everything until they end the session or it expires. |
| Session name | What the agent calls the session, so the owner can tell sessions apart. |
| Pairing link | The one-use link, also shown as a QR code, that the agent gives the owner to open the session on a phone. |
| Pairing card | The first card of every session: choose the emoji the agent named. |
| Target emoji | The one emoji on the pairing card that pairs the phone. Only the agent is told it. |
| Card | One question from the agent, with the options the agent wrote. |
| Option | One action the agent offers on a card. |
| Feedback | The owner's own words sent in place of an option. It closes the card. |
| Draft | A choice or feedback the owner has prepared but not sent. |
| Undo window | The short time after Send in which the owner can take an answer back. |
| Answer | What the owner sent for one card: an option or feedback. |
| Receipt | The service saying it stored an answer. Not an acknowledgement. |
| Acknowledgement | The agent saying it read an answer, with its next steps. |
| Queue | The open cards of a session. |
| History | The answered cards of a session, read-only. |
| Home screen | The owner's list of the sessions this browser holds, at `/app`. |
| Connect link | A link the owner copies from the phone to an agent, so the agent joins that phone directly. |
| Agent key, phone key | The secret each side holds to act in its session. |

## Statement

An owner can install one optional helper on an agent machine and use its guided setup to connect several supported agent clients there, while agents without the helper retain the complete remote HTTPS or MCP decision flow.

## Behaviors

1. Setup lists supported clients it finds, what each connection would change and any required client approval or restart. The owner chooses which clients to configure; merely discovering a client grants no authority.
2. One installation serves several client sessions on that machine. Repeating setup does not duplicate entries, replace unrelated settings or reset existing sessions. A failed or partial setup names what succeeded, what did not and how to undo the helper-owned changes.
3. Supported clients receive the AgentPager tools and usage guidance without the owner copying a server URL or editing files by hand. Client-required consent and authentication are surfaced, never bypassed; a missing prerequisite fails clearly.
4. Verification reports setup, delivery and status support separately for each selected client/version. A written configuration is not reported as a working connection until the relevant exchange succeeds. Setup verification creates no agent task; delivery stays unverified until a bound real-decision exchange demonstrates it.
5. Each agent session pairs independently and appears under its own agent/session name in the owning phone browser. The helper never shares a session or its credentials between agents merely because they share a host.
6. Disabling one client connection stops its helper integration and removes only changes setup recorded owning; other clients continue. A user-edited or ambiguous entry is reported for manual resolution rather than overwritten.
7. Without any helper installed, the owner can still pair, answer offered options or feedback, receive the agent's acknowledgement and revisit history through remote MCP or HTTPS. There is no helper prerequisite hidden in that path.

## Caveats

1. The support claim is limited to D6's recorded client, host and version combinations. Newly installed clients may need setup rerun, and already-running clients may need reload/restart.
2. One installation does not remove per-session phone pairing, vendor authentication or client-mandated trust prompts.
3. The helper is a same-user integration, not isolation between mutually hostile local processes or users.

## Statement

For a supported helper-connected session, an answer to its existing decision reaches the originating agent without requiring the model to keep calling a waiting tool; an idle running session can continue and a busy one receives the answer at its next safe turn boundary.

## Behaviors

1. Posting a decision returns after the service accepts it. The helper, rather than a model polling loop, maintains delivery while the agent performs independent work or becomes idle.
2. A committed owner answer is delivered only to the still-authorized session that posted the exact decision. Options and written feedback retain their existing limits and meaning; feedback closes that decision and is not a new-task channel.
3. A busy agent receives the answer at a safe turn boundary. The owner cannot steer its current turn through AgentPager. An idle running agent receives the answer as a continuation of the same session.
4. The owner can distinguish service receipt, helper receipt, queued delivery, uncertain delivery and the agent's own acknowledgement. Only an explicit agent acknowledgement names its next steps and confirms it read the answer.
5. If the helper or runtime is unreachable, the committed answer remains available within the session's lifetime. Reconnection checks authorization, proposal identity, terminal state and delivery outcome before attempting continuation; ambiguity is shown rather than hidden by a potentially duplicate submit.
6. Closing a runtime does not cause the helper to launch another. Pending input can wait for an explicitly supported resume. Unsupported or one-shot invocations are reported and use an explicit held-read path when they can; they are never advertised as automatic continuation.

## Caveats

1. Continued execution requires a supported runtime on an awake, connected host, valid vendor authentication and its normal permission policy. Receiving an answer does not bypass a pending native approval.
2. Acknowledgement is not proof that the agent performed the chosen action. The helper cannot constrain a model's interpretation of feedback merely by delivering it.
3. The adapter's atomicity and idempotency limits remain visible; this is not an exactly-once guarantee for external business actions.

## Statement

The owning phone shows whether each helper-connected agent session is live or unreachable and, when known, whether it is thinking, in a tool call or idle, without prompting the model or exposing its content.

## Behaviors

1. Only the phone browser already paired and authorized for that session may read its status; an unpaired claimant gains no status access. Connection and activity are separate: live requires fresh evidence that the helper can reach the relay and that the adapter remains connected to that agent session. Another session on the host being live is not sufficient.
2. A connection report older than 15 seconds is no longer shown as live. The owner sees unreachable and the last observation time; before any evidence, or when the phone cannot obtain fresh state, the view says unknown or stale rather than diagnosing the remote agent as unreachable.
3. A qualified adapter maps native runtime events to thinking (model generation), tool call or idle. The status includes no thought text, prompt, transcript, tool arguments or tool result. Missing, unsupported or incoherent activity evidence is unknown, not inferred idle.
4. Viewing or refreshing status reads the last observed state and its freshness. It never queues a prompt, triggers model inference, approves a tool or resumes work.
5. Ending, expiry or agent finish follows the existing terminal lifecycle. A finished session is shown as finished, never live simply because the helper still runs, and an ended/expired session cannot report new activity.
6. The complete decision flow works without helper telemetry. Non-helper sessions show status unavailable; they are not called unreachable merely because they use remote MCP.

## Caveats

1. The 15-second freshness threshold is a proposed owner-visible policy, not an observed performance result. No real-time claim is made while the phone cannot refresh.
2. Live means recently reachable, not healthy or making progress. Thinking reports a runtime phase, not the content or quality of reasoning.
3. Activity fidelity depends on qualified host APIs; absence of an event is not proof of idleness. A helper heartbeat alone proves neither agent connectivity nor activity.

## Statement

The helper exposes no phone-to-agent instruction channel: it returns answers to existing decisions and serves content-free status without expanding execution authority; existing pairing and session controls retain their own contracts.

## Clauses

1. A phone-originated request that would deliver input to an agent must name an authorized open decision and its exact proposal. A message without that binding, a different target agent, or a request type outside the closed answer protocol is refused before an adapter is invoked.
2. Written feedback remains an answer to that decision under C6. The protocol has no independent chat, task, status-prompt, steer, shell, file-write, process-launch or tool-permission operation.
3. Status reads only observed connection/activity state. They never ask an agent to summarize its work or consume an inference turn.
4. The helper neither changes agent sandbox/approval settings nor auto-approves native permission requests. An answer on an AgentPager card is not a native tool grant.
5. Installing or configuring the helper never installs arbitrary remote-specified code, accepts a client trust prompt, authenticates a client, or starts an agent task on the owner's behalf.

## Caveats

1. Authenticated feedback may still influence an agent with its existing permissions. A closed transport schema is not semantic confinement of model behavior or a read-only model sandbox.
2. A compromised owner endpoint can submit valid answers in its authorized scope. Hostile same-user code, compromised client runtimes and a compromised installer/update signer are outside this invariant's assurance boundary.

## Statement

A helper delivers only authorized, unexpired answers to their locally bound agent session and exact proposal, preserves delivery uncertainty across retries and restarts, and cannot revive ended or finished authority.

## Clauses

1. Local binding fixes the helper host, client instance, real agent-session identity, AgentPager session and pending proposal identity. A remote message cannot choose an executable, path, environment, prompt template or a different session binding.
2. Before submission, the helper validates the authorized answer, decision and answer IDs, proposal identity, session lifecycle and freshness against the bound state. Unknown, modified, cross-session, revoked or over-limit inputs are refused whole.
3. Duplicate notifications and repeated reads converge on one delivery record. A crash or timeout between submission and receipt is uncertain unless the adapter can establish a safe outcome; the helper does not blindly queue it again. Queue acceptance never fabricates an agent acknowledgement.
4. End, expiry, finish or explicit local disconnect invalidates pending continuation. The helper rechecks lifecycle before any new submission, clears local payloads/credentials when the existing retention contract requires it, and does not rebind the session automatically on restart. Input already accepted by a runtime cannot be claimed to have been recalled.
5. The helper uses only scoped local communication and outbound relay connections; it opens no remotely reachable command listener. A client adapter invokes only a locally authorized integration with structured parameters, without shell interpolation of remote content.
6. Relay credentials are absent from model tool arguments, process arguments and routine logs in the helper path. Status carries only state/time metadata. Resource and retry bounds are enforced locally as well as by the service and reviewed before activation.

## Caveats

1. Unless the owner chooses and approves a separate end-to-end authenticity design, the relay remains trusted to authenticate owner answers and see plaintext. This invariant does not survive a malicious relay fabricating an otherwise valid answer. TLS is not an end-to-end owner signature.
2. A service-delivered browser client is also part of that trust boundary. Keeping keys on a phone does not remove the relay from trust if it can replace the code using them.
3. Expiry/revocation prevents subsequent submissions; it does not undo input already accepted by the agent or external actions already performed. Exact business-action-once behavior remains the agent/tool system's responsibility.
4. OS/runtime compromise and provider backups are not covered. Credential containment from model context is not isolation from unrestricted same-user code.

Keep history; narrow the assumptions that block the helper.

The old agent-reach decision said a helper added nothing beyond curl/MCP. Setup across clients, observed activity and native continuation give it a distinct purpose. Preserve that record as history; a later owner approval record should supersede only that rejected-helper rationale.

# AgentPager

## Vision

AgentPager makes it easy for me to leave my agents working on my computer or in a cloud VM and send owner decisions to my phone so they can continue to do useful work while I am away.

## Strategic capabilities

### SC1 · Unblock my agent from my phone

Connect my agent to my phone easily: the agent gives me a QR code or a link, or I copy a link from my phone to give the agent. To pair, the agent sends me a decision with five random emoji and tells me which one to choose.

Once paired, my agent sends me a multiple-choice decision when it needs me. I answer, see that my answer was sent, and get the agent's acknowledgement and its next steps. I can look back at past decisions.

Decision cards can show the exact email, pull request, calendar invitation or reply, the way that product would show it, with the agent's options for what to do with it. The agent carries out the option I chose; AgentPager only carries my answer.

Accounts should let me return across devices without making a guest session public.

<!-- Learn whether owners value longer sessions before building subscriptions. -->

## Strategic invariants

### SI1 · Sending a decision requires confirmation

Following good UX practice, an action that cannot be undone needs a confirming step. So an answer always takes two taps: I choose an option or write a response, then press Send. Choosing alone never sends. The agent receives exactly what I sent.

### SI2 · Only the first phone gets in

The first phone to claim a pairing link reserves the session; later devices are refused, and the first keeps it. Choosing the emoji the agent showed and pressing Send pairs it; a wrong choice leaves it unpaired. Pairing links are unguessable and work once. A lost phone means a new session, never a transfer.

### SI3 · Sent decisions cannot be changed

I can reread the question, my answer and the agent's acknowledgement, but not change them.

### SI4 · An acknowledgement always comes from the agent

An acknowledgement is a real message from the agent, never an automatic message from AgentPager. The phone tells apart "your answer was sent" from "your agent received it".

### SI5 · A free session ends when I end it, or 24 hours after pairing

When my agent finishes, I can still read the session until it ends. Once a session ends or expires, its decisions are deleted.

### SI6 · UTF-8 with Markdown is allowed; invalid or over-limit text is refused, never truncated

Card titles, option labels, option detail and agent acknowledgements allow 280 visible characters; question detail and my written feedback allow 1,000. Count spaces and Markdown punctuation. Text is valid UTF-8 with Markdown and no HTML. Anything else is refused whole, with an error that tells the agent what to fix. Nothing is truncated or silently cleaned. On screen, titles, option labels and session names show each run of spaces and line breaks as one space; detail text shows them as sent.

### SI7 · Cards are independent

Several cards can be open at once and answered in any order. Answering one never changes another.

### SI8 · Approval refers to the exact proposal

Before I answer a rich card, I see its complete target and content, and my answer refers to exactly that version.

### SI9 · Research never pretends to be an available paid upgrade

A Pro research offer takes no payment and changes nothing about my sessions. It sends my feedback only with my consent.

## Strategic goals

### SG1 · Return to completed work, not an unseen question

I can walk away while my agent works and come back to finished work, not a question I never saw. Later, measure the stops prevented and the time or tokens unblocked.

### SG2 · Agents use a helpline instead of bad decisions

An agent that is blocked or unsure about a risky step asks me for a quick go/no-go instead of stopping or taking the risk. Later, measure fewer bad decisions and unnecessary stops.

### SG3 · Learn which paid value can sustain the product

Test whether owners need longer-running agents, for which work, and whether $2.99 a month fits that value. Clicks and surveys show interest, not revenue.

## Strategic principles

### SP1 · Make the usual answer easy and clear

Use plain language I can understand without specialist knowledge. Always offer feedback, except on the pairing card, for when the options do not fit; feedback is the fallback, not the usual path.

### SP2 · Keep the first version focused and its foundations explicit

Serve one agent and one phone per session. Accounts, native apps, community cards and paid plans need their own design and user learning. Run on a Cloudflare Worker at agentpager.me, with one SQLite-backed Durable Object per session. Agents reach one service by plain HTTPS or a remote MCP server. Defer Alchemy until a date the owner sets.

### SP3 · Agents choose the options; AgentPager keeps them easy to answer

For every card, the agent chooses the question, two to five options and their emoji. Each option is one target, its emoji and title, with no radio, check or number. The emoji tells options apart, so I can refer to them in feedback, such as "do 🚀 and then 🛠️". I choose one option, never several. On a product card the options are the actions the agent offers, such as Send now or Send tomorrow.

### SP4 · Keep the decision short; make detail optional

Aim for about 100 characters for the question and for each option. The agent may name the option it recommends; it shows under the question, with the question's detail as a short reason, never a second question. Nothing is chosen for me. Each option may carry about 200 characters of detail, shown only while it is chosen. These are writing guides; SI6 sets the hard limits.

### SP5 · Reach the agents owners actually use

Any agent whose client can send HTTPS requests or add an MCP server can use AgentPager from agentpager.me/start alone, with nothing to install. That covers terminal agents, desktop and IDE apps, and chat apps on my phone. /start is written for developers of every level. A waiting agent has my answer within a second of the Undo window closing.

### SP6 · Let owners choose progressive enhancement

The full decision flow must work without installing our helper. Owners who choose more setup should gain a simpler way to connect several supported agents on a machine and more dependable answer delivery, without turning AgentPager into a general remote-control channel.

Connect my agent to my phone easily: the agent gives me a QR code or a link, or I copy a link from my phone to give the agent. To pair, the agent sends me a decision with five random emoji and tells me which one to choose.

Once paired, my agent sends me a multiple-choice decision when it needs me. I answer, see that my answer was sent, and get the agent's acknowledgement and its next steps. I can look back at past decisions.

Decision cards can show the exact email, pull request, calendar invitation or reply, the way that product would show it, with the agent's options for what to do with it. The agent carries out the option I chose; AgentPager only carries my answer.

Accounts should let me return across devices without making a guest session public.

<!-- Learn whether owners value longer sessions before building subscriptions. -->

## Strategic invariants

### SI1 · Sending a decision requires confirmation

Following good UX practice, an action that cannot be undone needs a confirming step. So an answer always takes two taps: I choose an option or write a response, then press Send. Choosing alone never sends. The agent receives exactly what I sent.

### SI2 · Only the first phone gets in

The first phone to claim a pairing link reserves the session; later devices are refused, and the first keeps it. Choosing the emoji the agent showed and pressing Send pairs it; a wrong choice leaves it unpaired. Pairing links are unguessable and work once. A lost phone means a new session, never a transfer.

### SI3 · Sent decisions cannot be changed

I can reread the question, my answer and the agent's acknowledgement, but not change them.

### SI4 · An acknowledgement always comes from the agent

An acknowledgement is a real message from the agent, never an automatic message from AgentPager. The phone tells apart "your answer was sent" from "your agent received it".

### SI5 · A free session ends when I end it, or 24 hours after pairing

When my agent finishes, I can still read the session until it ends. Once a session ends or expires, its decisions are deleted.

### SI6 · UTF-8 with Markdown is allowed; invalid or over-limit text is refused, never truncated

Card titles, option labels, option detail and agent acknowledgements allow 280 visible characters; question detail and my written feedback allow 1,000. Count spaces and Markdown punctuation. Text is valid UTF-8 with Markdown and no HTML. Anything else is refused whole, with an error that tells the agent what to fix. Nothing is truncated or silently cleaned. On screen, titles, option labels and session names show each run of spaces and line breaks as one space; detail text shows them as sent.

### SI7 · Cards are independent

Several cards can be open at once and answered in any order. Answering one never changes another.

### SI8 · Approval refers to the exact proposal

Before I answer a rich card, I see its complete target and content, and my answer refers to exactly that version.

### SI9 · Research never pretends to be an available paid upgrade

A Pro research offer takes no payment and changes nothing about my sessions. It sends my feedback only with my consent.

## Strategic goals

### SG1 · Return to completed work, not an unseen question

I can walk away while my agent works and come back to finished work, not a question I never saw. Later, measure the stops prevented and the time or tokens unblocked.

### SG2 · Agents use a helpline instead of bad decisions

An agent that is blocked or unsure about a risky step asks me for a quick go/no-go instead of stopping or taking the risk. Later, measure fewer bad decisions and unnecessary stops.

### SG3 · Learn which paid value can sustain the product

Test whether owners need longer-running agents, for which work, and whether $2.99 a month fits that value. Clicks and surveys show interest, not revenue.

## Strategic principles

### SP1 · Make the usual answer easy and clear

Use plain language I can understand without specialist knowledge. Always offer feedback, except on the pairing card, for when the options do not fit; feedback is the fallback, not the usual path.

### SP2 · Keep the first version focused and its foundations explicit

Serve one agent and one phone per session. Accounts, native apps, community cards and paid plans need their own design and user learning. Run on a Cloudflare Worker at agentpager.me, with one SQLite-backed Durable Object per session. Agents reach one service by plain HTTPS or a remote MCP server. An optional helper connects supported clients on their own machines to that same service; each agent and phone still have an independent session. Defer Alchemy until a date the owner sets.

### SP3 · Agents choose the options; AgentPager keeps them easy to answer

For every card, the agent chooses the question, two to five options and their emoji. Each option is one target, its emoji and title, with no radio, check or number. The emoji tells options apart, so I can refer to them in feedback, such as "do 🚀 and then 🛠️". I choose one option, never several. On a product card the options are the actions the agent offers, such as Send now or Send tomorrow.

### SP4 · Keep the decision short; make detail optional

Aim for about 100 characters for the question and for each option. The agent may name the option it recommends; it shows under the question, with the question's detail as a short reason, never a second question. Nothing is chosen for me. Each option may carry about 200 characters of detail, shown only while it is chosen. These are writing guides; SI6 sets the hard limits.

### SP5 · Reach the agents owners actually use

Any agent whose client can send HTTPS requests or add an MCP server can use AgentPager from agentpager.me/start alone, with nothing to install. That covers terminal agents, desktop and IDE apps, and chat apps on my phone. /start is written for developers of every level. A waiting agent has my answer within a second of the Undo window closing.

### SP6 · Let owners choose progressive enhancement

The full decision flow must work without installing our helper. Owners who choose more setup should gain a simpler way to connect several supported agents on a machine and more dependable answer delivery, without turning AgentPager into a general remote-control channel.

Prove the cross-client experience and its failure boundaries.

The proposed D6 roster exercises two client families on a Linux VM and CLI/desktop on macOS. It is an acceptance target, not a support claim. K2 measures actual native turn start separately from K1’s delivery to a caller already waiting. J3 and J4 cover the combined owner walk and reconnect/misuse/lifecycle cases.

  1. Install once on the VM, connect Codex CLI and Pi, pair two independent sessions to one browser and observe real activity events.
  2. Answer both after their turns go idle, out of order and including feedback. Each exact session continues and acknowledges.
  3. Disconnect/restart, cross identities, replay messages, interrupt submission and end/expire a session before reconnection. Keep uncertainty honest and authority scoped.
  4. Finish a fresh no-helper remote-MCP exchange without local tools or borrowed helper credentials.

## Statement

The helper's setup, delivery and activity claims stand on explicitly qualified external agent runtimes and host environments, with each client capability and its limits recorded separately.

## Provided

1. A Linux x64 VM with Codex CLI and Pi, and a macOS arm64 host with Codex CLI and the Codex desktop coding-agent experience, installed and authenticated through owner-supplied legitimate access. Their exact OS, binary provenance, client and adapter versions, invocations and agent-backend locations are recorded by the recipe before approval; none is invented from a model's memory.
2. Native client interfaces capable of registering tools, preserving real session identity, delivering a follow-up answer without a model wait loop and reporting generation/tool-call/idle events. The helper and its adapters are product code, not supplied dependencies; client support is qualified against the actual interfaces they use.
3. A per-client matrix separates setup, answer wake-up and activity telemetry. A missing interface is an explicit unsupported capability and cannot satisfy a required case through transcript scraping, a fake event source or a manual prompt.
4. A host service mechanism that can keep the helper running after setup or terminal closure without requiring administrator privileges. The recipe records startup, shutdown, state placement, permissions and the effect of sleep/offline conditions. Client-required approvals remain visible to the owner.

## Never

1. Treat an installed executable or shared configuration file as proof of working desktop wake-up or telemetry, change global client configuration outside the owner-approved helper setup, or borrow credentials the owner did not supply.
2. Present Claude, another client, a new architecture or an unqualified version as supported merely because a protocol could theoretically connect it.

## Proof runs on

1. A real Linux VM with at least one simultaneous Codex CLI session and one Pi session, through one installed helper and the deployed relay, with one owning phone browser and independently paired sessions.
2. The macOS host with actual CLI and desktop sessions, through the same relay, testing setup, answer delivery and native activity evidence separately. Qualification records preserve failed attempts and identify any unsatisfied required case.
3. Existing no-helper HTTPS and remote-MCP paths against real clients, plus prior product regression proof. Host timing and vendor responses are not mocked; deterministic fault injection supplements rather than replaces the real client walks.

## Caveats

1. This draft names a proposed acceptance roster, not verified support. If a required client lacks a suitable API, revise the roster or design with the owner before activation; the builder must not silently weaken activity or delivery claims.
2. Virtualized and sampled hosts do not prove every OS, machine, account policy or future client version. Installing the helper on a laptop does not give it authority over a different VM or backend.

## Statement

On qualified awake, connected helper/client combinations, an existing answer starts an idle agent's next turn promptly without model polling, and a busy agent receives it promptly after its next safe idle boundary.

## Probe

1. Record candidate, host/client/adapter versions, target, network, local binding and runtime event timestamps. Use D6's real environments and the deployed relay, with production timing policy.
2. For each required client/host combination, perform five idle-session and five busy-session exchanges. Record committed answer acceptance after Undo, the runtime's safe idle boundary where applicable, native turn start, the agent's answer read and explicit acknowledgement.
3. Report every sample and failure. Confirm the agent had no waiting tool open; distinguish transport receipt, queue acceptance, actual turn start and agent acknowledgement. Pairing and inference completion time are not relay latency.
4. Run K1 separately for the no-helper held-read caller. Passing K2 cannot replace the older waiting-agent proof or imply that the phone is background-notified.

## Bar

Every idle sample starts a native turn within five seconds of committed answer acceptance. Every busy sample starts the answer turn within five seconds of the runtime's next safe idle boundary after acceptance. Every sample reads the exact answer and emits an explicit acknowledgement; any wrong session, duplicate answer turn or error fails. These proposed thresholds apply only to the sampled qualified combinations, not offline/exited runtimes or all networks.

## Caveats

1. The five-second thresholds are proposed for owner review, not measurements. Five samples per case are a smoke bar, not an availability or battery-life guarantee.
2. Work already accepted into a runtime, queue congestion, host sleep and expired authentication have separate lifecycle outcomes; no process restart or machine wake is measured.

## Statement

An owner installs one helper on a spike VM, connects two supported client families, pairs their separate sessions to one phone browser and answers both while observing their native activity.

## Steps

1. Use guided setup once on the Linux VM to connect its real Codex CLI and Pi clients, preserving unrelated configuration; start one session in each and pair both independently to the same phone browser.
2. Observe generation, a tool call and idle for each session through real runtime events. Refresh phone status while idle and verify no model turn or prompt is created.
3. Post one decision from each agent and let both turns become idle. Answer the second with feedback, then the first with an option. Each answer resumes only its originating session and receives that agent's acknowledgement.
4. Rerun setup and disconnect one client. Its helper integration stops, the other session continues, and neither client's unrelated settings or session history changes.
5. Complete a separate fresh no-helper remote-MCP decision flow, including feedback and acknowledgement, without using the installed helper's local tools or credentials.

## Caveats

1. The shortest product journey remains J1 and the longest current session remains J2; this is an additional cross-client setup and isolation walk, not their replacement.
2. The two-family VM target is sampled, not universal agent support or machine-wide pairing. A passing phone-browser walk does not prove native notifications.

## Statement

During a helper disconnect and restart, independent sessions preserve their answers and honest status, refuse crossed or revoked delivery, and never turn a retry into an arbitrary or duplicate instruction.

## Steps

1. Pair two real sessions through one helper. Disconnect its relay connection, commit an answer on the phone, and observe stale/unreachable connection state without fabricating idle activity or agent acknowledgement.
2. Restore connectivity and restart the helper with its state preserved. Deliver the still-valid answer to its exact session; replay its event and attempt to cross its decision/session identities. No second answer turn or wrong-session submission occurs.
3. Interrupt submission at an adapter boundary where the result is unknown. After restart the UI still distinguishes uncertain from acknowledged; it does not claim success or blindly repeat a possibly accepted queue call.
4. With another pending answer, end or expire that session before reconnection. Reconnect and confirm no new continuation submission, cached content recovery or session resurrection. Input already accepted before termination is reported separately.
5. Attempt an unsolicited message and a status request carrying a prompt, arbitrary session target or execution parameter. Each is refused before the adapter; ordinary status viewing still creates no inference turn.
6. Re-run the independent remaining session's normal answer and acknowledgement flow, confirming that failure or revocation of one session did not end or redirect the other.

## Caveats

1. Real clients establish integration; deterministic crash-boundary cases additionally exercise the adapter protocol. A bounded failure campaign does not prove every process schedule or provider fault.
2. Relay or endpoint compromise is governed by I10's explicit trust caveats; invalid-input tests are not a proof of resistance to a malicious trusted relay.
