# Plannotator Inbox delivery: source notes

Researched 2026-10-27. Read-only source inspection at Plannotator commit [`a104c2068f23ec9cc95c5216ad4f679aa8c9bde2`](https://github.com/backnotprop/plannotator/tree/a104c2068f23ec9cc95c5216ad4f679aa8c9bde2). No product installation, credentials, or live delivery test. “Verified” below means verified in this source snapshot, not measured against a running host.

## Main finding

**Verified:** the apparent push experience comes from a process inside the agent harness that can submit a new user turn. For Claude Code, Pi and OpenCode 2, the network side is actually **long polling below the model**, with a held local HTTP request. The agent need not spend turns calling a waiting tool. Codex is different: the Inbox invokes `codex queue` itself. Browser updates use SSE; this is a separate channel from agent delivery.

## Claude Code

- **Verified:** a per-session `InboxLink` proxies tools to the local Inbox MCP endpoint, filling the actual session ID and project. A one-second timer manages idle state and a background bridge poll. The held poll asks for 20 seconds; failed connections back off from 5 to 60 seconds. Pending replies wait for two consecutive idle ticks. [Connection description and constants](https://github.com/backnotprop/plannotator/blob/a104c2068f23ec9cc95c5216ad4f679aa8c9bde2/apps/hook/hooks/mod/inbox.ts#L16-L48), [poll implementation](https://github.com/backnotprop/plannotator/blob/a104c2068f23ec9cc95c5216ad4f679aa8c9bde2/apps/hook/hooks/mod/inbox.ts#L628-L666).
- **Verified:** ordinary delivery calls `$.prompt.submit({ text })`; explicit Send now can append a user message with `$.session.append`, so the next model request sees it during an existing turn. The adapter checks an append refusal. [Actual host adapter](https://github.com/backnotprop/plannotator/blob/a104c2068f23ec9cc95c5216ad4f679aa8c9bde2/apps/hook/hooks/mod/register.ts#L178-L198), [delivery implementation](https://github.com/backnotprop/plannotator/blob/a104c2068f23ec9cc95c5216ad4f679aa8c9bde2/apps/hook/hooks/mod/inbox.ts#L831-L907).
- **Documented host requirement:** Plannotator plugin plus its mod, Claude Code 2.1.287 or later. Send now has a separate 2.1.301 floor in code. This is a hooks-module integration with live engine APIs, not merely an ordinary shell hook returning text. [Inbox docs](https://plannotator.ai/docs/reference/inbox/#claude-code), [append version gate](https://github.com/backnotprop/plannotator/blob/a104c2068f23ec9cc95c5216ad4f679aa8c9bde2/apps/hook/hooks/mod/inbox.ts#L74-L82).

## Pi and OpenCode

- **Verified:** both share `InboxWake`. It holds a 20-second local bridge request, runs a one-second management tick and delays ordinary delivery for two idle ticks. Leases choose the most recently used host process when two processes have the same session open; atomic claim directories coordinate individual replies. [Shared connection](https://github.com/backnotprop/plannotator/blob/a104c2068f23ec9cc95c5216ad4f679aa8c9bde2/packages/shared/inbox/agent-link.ts#L18-L29), [timing constants](https://github.com/backnotprop/plannotator/blob/a104c2068f23ec9cc95c5216ad4f679aa8c9bde2/packages/shared/inbox/agent-link.ts#L58-L73).
- **Verified:** Pi extension calls `pi.sendUserMessage(text, { deliverAs: "followUp" })`; Send now uses `"steer"`. It checks idle/pending-message state and whether a run settled. Delivery completes when Pi starts that user message, with a watchdog for failures. Wake setup requires an interactive UI; print/JSON runs do not have it. [Pi integration](https://github.com/backnotprop/plannotator/blob/a104c2068f23ec9cc95c5216ad4f679aa8c9bde2/apps/pi-extension/inbox.ts#L19-L35), [actual send and target](https://github.com/backnotprop/plannotator/blob/a104c2068f23ec9cc95c5216ad4f679aa8c9bde2/apps/pi-extension/inbox.ts#L230-L267), [interactive activation](https://github.com/backnotprop/plannotator/blob/a104c2068f23ec9cc95c5216ad4f679aa8c9bde2/apps/pi-extension/inbox.ts#L305-L324).
- **Verified:** OpenCode 2 plugin calls `session.prompt` with `delivery: "queue"`, or `"steer"` for Send now. It uses runtime events plus bounded idle probes; older OpenCode has the tool but no wake. [Runtime distinction](https://github.com/backnotprop/plannotator/blob/a104c2068f23ec9cc95c5216ad4f679aa8c9bde2/apps/opencode-plugin/inbox.ts#L1-L30), [actual prompt calls](https://github.com/backnotprop/plannotator/blob/a104c2068f23ec9cc95c5216ad4f679aa8c9bde2/apps/opencode-plugin/inbox.ts#L597-L643).

## Codex

- **Verified:** there is no Plannotator Codex plugin. The stdio MCP shim learns the thread ID from tool-call metadata; the server checks a queue-capable Codex CLI. Persistent sessions qualify, while `codex exec` is excluded. Minimum version is 0.149.0 in Plannotator's code. [Core contract](https://github.com/backnotprop/plannotator/blob/a104c2068f23ec9cc95c5216ad4f679aa8c9bde2/packages/core/inbox-codex.ts#L1-L17), [server description](https://github.com/backnotprop/plannotator/blob/a104c2068f23ec9cc95c5216ad4f679aa8c9bde2/packages/server/inbox-codex-wake.ts#L1-L40).
- **Verified:** it executes the CLI directly with an argv array: `codex queue --thread=<id> --message=<text>`. No terminal typing or shell interpolation. This does expose reply text transiently in the process list. [Actual execution and results](https://github.com/backnotprop/plannotator/blob/a104c2068f23ec9cc95c5216ad4f679aa8c9bde2/packages/server/inbox-codex-wake.ts#L309-L366).
- **Documented upstream behavior, not independently exercised:** idle threads run the queued turn quickly; busy threads take it next; closed threads take it on resume. Source comments also mention a background-server headless case. Treat those timing/lifecycle claims as Plannotator's compatibility assumptions until tested against our supported Codex versions.
- **Verified:** exit 0 means queued, not delivered. Later tool metadata or explicit reads establish delivery. It persists a per-item/thread claim before invoking the CLI. A timeout is ambiguous and is never automatically resubmitted; the reply remains available to read. This favors avoiding duplicate turns over guaranteeing delivery. Unknown threads become ended; other CLI failures retry. [State semantics](https://github.com/backnotprop/plannotator/blob/a104c2068f23ec9cc95c5216ad4f679aa8c9bde2/packages/server/inbox-codex-wake.ts#L21-L40), [result handling](https://github.com/backnotprop/plannotator/blob/a104c2068f23ec9cc95c5216ad4f679aa8c9bde2/packages/server/inbox-codex-wake.ts#L325-L366).
- **Verified:** this dispatch is triggered by store events and selected retry/start/resume events, not a model polling loop. A concurrent `wait_for_reply` suppresses queueing that reply. [Sweep](https://github.com/backnotprop/plannotator/blob/a104c2068f23ec9cc95c5216ad4f679aa8c9bde2/packages/server/inbox-codex-wake.ts#L374-L435).

## Shared relay and fallback

- **Verified:** `/api/inbox/bridge/poll` returns immediately if pending data exists; otherwise it subscribes to store events and holds the request until a message, abort or timer. The server caps this at 25 seconds. It is event-woken long polling rather than periodically querying storage while held. [Server implementation](https://github.com/backnotprop/plannotator/blob/a104c2068f23ec9cc95c5216ad4f679aa8c9bde2/packages/server/inbox.ts#L1914-L1950).
- **Verified:** unsupported clients call `wait_for_reply`. Its 50-second default is another store-event subscription with a timer; timeout returns a cursor. Thus they retain a model/tool wait loop. [Default](https://github.com/backnotprop/plannotator/blob/a104c2068f23ec9cc95c5216ad4f679aa8c9bde2/packages/server/inbox-mcp.ts#L42-L43), [wait implementation](https://github.com/backnotprop/plannotator/blob/a104c2068f23ec9cc95c5216ad4f679aa8c9bde2/packages/server/inbox-mcp.ts#L1211-L1252).
- **Verified:** the user-facing browser listens to SSE with `EventSource`, preserving an event cursor on reconnect. This does not by itself wake an agent. [Browser event client](https://github.com/backnotprop/plannotator/blob/a104c2068f23ec9cc95c5216ad4f679aa8c9bde2/packages/inbox/api.ts#L1003-L1022).
- **Verified:** feedback becomes formatted prompt text with a subject, message ID, fixed provenance/instruction line, verbatim body, and thread/tool pointers. It is not a distinct model-native decision channel. [Formatting implementation](https://github.com/backnotprop/plannotator/blob/a104c2068f23ec9cc95c5216ad4f679aa8c9bde2/packages/shared/inbox/connection.ts#L811-L875).

## Trust and security boundary

- **Verified:** normal Inbox binds loopback. Bridge/control endpoints require the correct loopback Host, no Origin, and a bearer token; token storage is an owner-only registry file. Browser writes use origin checks and a server-session nonce. [Server boundary](https://github.com/backnotprop/plannotator/blob/a104c2068f23ec9cc95c5216ad4f679aa8c9bde2/packages/server/inbox.ts#L22-L37), [route enforcement](https://github.com/backnotprop/plannotator/blob/a104c2068f23ec9cc95c5216ad4f679aa8c9bde2/packages/server/inbox.ts#L2241-L2275), [registry permissions](https://github.com/backnotprop/plannotator/blob/a104c2068f23ec9cc95c5216ad4f679aa8c9bde2/packages/shared/inbox/registry.ts#L109-L121).
- **Verified limitation:** local MCP has no authentication token; it rejects browser Origins and remote Hosts. Consequently the design trusts local non-browser processes, and its shared registry token is not per-agent isolation. Same-user untrusted code is not contained by this design. [MCP route](https://github.com/backnotprop/plannotator/blob/a104c2068f23ec9cc95c5216ad4f679aa8c9bde2/packages/server/inbox.ts#L2241-L2261).
- **Documented remote boundary:** supported Tailscale publishing goes through a separate owner-identity-checked listener, with agent routes kept local. This replaces AgentPager's public cloud relay with tailnet membership and local-machine availability. Source also contains a separate feature-gated phone surface, so “no mobile functionality” would be too broad. [Listener overview](https://github.com/backnotprop/plannotator/blob/a104c2068f23ec9cc95c5216ad4f679aa8c9bde2/packages/server/inbox.ts#L6-L19), [remote access docs](https://plannotator.ai/docs/reference/inbox/#over-your-tailnet).

## Implication for AgentPager (inference)

The transferable idea is a trusted local companion that holds the transport open and binds each answer to a real harness session, then uses a supported queue/follow-up API to wake it. Choosing WebSocket or SSE instead of long polling is secondary. A compiled Bun binary can house that companion, broker secrets outside model context, validate envelopes and manage a durable outbox, but cannot create a wake API in a host that lacks one. Extensions provide that host-specific capability for Pi/Claude/OpenCode; Codex may need only its existing queue CLI. These are architectural inferences, not implemented AgentPager changes or a complete security audit.
