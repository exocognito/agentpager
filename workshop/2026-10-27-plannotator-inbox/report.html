1. What makes Inbox feel different

There are three independent problems:

  1. Transport: how a human answer gets from storage to a client process.
  2. Session delivery: how that process inserts the answer into the correct conversation and starts another turn.
  3. Receipt: how the owner learns whether it was merely stored, queued, read, or acted on.

Plannotator supplies client-specific machinery for the second problem. It can return from send_message, let the agent do other work or go idle, then deliver the reply into that conversation. This is materially better than relying on the model to remember another read.

The delivered feedback is formatted prompt text: subject, message ID, provenance line, the owner's body, and thread/tool references. There is no special decision format that makes the model listen by itself; the host API schedules the turn. Structured IDs and explicit provenance are still worth copying. Prompt formatter.

It still polls. Its native agent links long-poll a local /api/inbox/bridge/poll route with a 20-second hold; Claude's mod schedules work on a one-second host tick. This is ordinary code, not recurring model turns. A held request can return immediately when the answer arrives: the hold length is not an extra 20-second delivery delay. Unsupported clients use wait_for_reply, up to 50 seconds per call. Agent-link implementation, Claude Inbox implementation.

Official Claude Channels are local stdio MCP servers declaring claude/channel and emitting notifications/claude/channel. Claude queues incoming events for processing; events only arrive while the session is open. Notification write success is not a processing acknowledgement, and policy can silently discard events. They are a research preview; custom channels require a development flag and interactive confirmation rather than ordinary allowlisted production installation. Organization policy and authentication/provider restrictions also apply. This is a promising experiment, not evidence we can ship AgentPager as a generally available channel today. Channels can separately relay native tool approvals using a request ID and allow/deny verdict. That would let AgentPager carry a real harness permission request rather than only a model-authored decision card. It adds authority and should be a separate, explicitly designed capability; merely receiving an owner comment must not grant native tool permission. 3. How this compares with AgentPager today

AgentPager already specifies a 50-second held answer read and delivery within one second of accepted Send to a waiting caller. The phone polls every three seconds. Its MCP server is stateless Streamable HTTP, with session authority in tool arguments. C2 records that a stopped agent is not woken; the owner has clarified that this is not a hard requirement. Treat it as the current contract's limitation, not a constraint on these options. Answer contract, routes and authentication, C2, K1.

Therefore the likely gain is fewer repeated wait calls and reliable continuation across idle turns, not a demonstrated latency improvement. A shell program can loop over the existing held-read API without consulting the model, but it still needs a host adapter to wake a finished turn. A socket to an idle process does not itself schedule inference.

SP5 separately promises nothing to install for agents with HTTPS or custom MCP. That reach has value, especially for hosted chat apps, but should be weighed against reliable continuation rather than treated as a veto on native integration. My revised recommendation is an installed bridge as the primary experience for supported coding agents, with a generic compatibility path where feasible. If installation becomes mandatory, explicitly revise SP5; before promising wake-up, update C2, D2 client qualification, K1 measurement and routes. Strategy, client dependency.

What changes when no-wake is disregarded

The technical options were already available. Their ranking changes: automatic continuation becomes part of the intended product behavior, and a local install can be justified by that behavior rather than presented only as an optional enhancement. A single bridge executable with thin host adapters is the preferred first architecture. A new agent launcher or a client built around an SDK/app-server becomes worth considering if AgentPager must also restart exited agents, but neither is required just to wake an idle session.

Owning the launcher gives AgentPager more reliable process lifecycle control, at the cost of asking users to start agents through it. Owning an entire SDK/app-server client gives even more control and more maintenance. Start with adapters into existing clients; add a managed launcher only if exited-process recovery proves essential. These are architectural judgments, not tested compatibility claims.

4. Does a Bun binary help?

Yes as distribution. Bun can bundle JavaScript/TypeScript, dependencies and its runtime into one executable, built per target OS/architecture. The user need not separately install Bun or Node. Compilation does not confer a host messaging API, sandbox the process, authenticate the owner or encrypt the relay. Bun executable documentation.

A proposed agentpager bridge could own pairing credentials, HTTP/MCP calls, durable delivery state and a Codex queue adapter. A Pi extension could call the same core or connect through a narrowly scoped local interface. A Claude Channels subprocess could use the same protocol. For a first spike, use the existing held-read endpoint from ordinary code: a new transport is not needed to prove the main UX improvement. If subscriptions are later justified, an outbound authenticated WebSocket to the existing session Durable Object avoids inbound ports on the user's machine. Cloudflare supports Durable Object WebSockets and hibernation; actual billing and reconnect behavior need measurement, not assumptions. Cloudflare WebSocket guidance.

An extension alone can own the connection for a supported client. A separate daemon becomes useful if we want one connection manager across agents, durable queues independent of agent restarts, or a shared protected credential store. Avoid requiring both a daemon and extensions until that benefit is demonstrated.

5. Security: what improves, what changes

Assessment: push versus polling is not an authentication boundary. A local bridge can reduce accidental exposure by keeping the AgentPager capability out of model arguments and transcripts. It also becomes installed code capable of delivering prompts to powerful agents. Same-user arbitrary code or an unrestricted shell can generally undermine a same-user bridge; hiding keys from model context is not isolation from that agent's process authority.

Plannotator itself trusts local non-browser processes: its local MCP endpoint has no token, while bridge/control routes use a shared owner-readable token plus loopback Host/no-Origin checks. Browser-origin defenses are useful but are not per-agent access control. That local trust assumption should be an explicit choice rather than an accidental consequence of installing a binary. Boundary and enforcement, registry permissions.

Proposed propertyWhat is required; what it actually protects

These are design requirements and threat-model judgments, not properties tested here. E2EE would materially change server-side validation/rendering and recovery: authenticate ciphertext envelopes and validate plaintext at endpoints; account for the browser UI delivery trust boundary, which can undermine encryption if the server serves malicious client code. Plannotator's source contains phone/relay encryption work, but its public Inbox reference emphasizes loopback/tailnet access; published availability was not established. Do not claim its entire phone model is shipped or equivalent to ours. Phone/relay security design and stated proof.

One concrete Plannotator tradeoff to avoid copying: it puts the human's feedback in the codex queue --message process arguments, briefly visible to process inspection. An AgentPager spike could instead queue only an opaque answer/event reference and ask the model to retrieve that exact answer via a local tool. This adds one purposeful read after wake but keeps feedback out of argv. It does not keep the eventual answer out of the model transcript. Alternatively evaluate app-server IPC when lifecycle ownership and stability permit. Explicit argv caveat in source.

Keep SI4 intact: neither bridge transport receipt nor codex queue success should produce the existing agent acknowledgement. Only the agent's explicit acknowledgement of the stored answer and next steps should do that. I6.

6. A small next experiment

Recommendation, not implementation authorization: prove Codex first because the machine already exposes the required queue command. Treat automatic continuation as the target default for supported coding agents. Add Pi as the next adapter; evaluate Claude Channels separately for preview restrictions. A required local install is a reasonable trade if these clients define the target audience; it is not technically necessary to require a separate plugin for every client. Prove host wake-up before rewriting the cloud transport.

Acceptance criteria for the experiment:

  1. Agent posts a decision, returns from its tool call and goes idle. Owner answers from the phone; the exact originating thread starts again without a model polling loop.
  2. Busy thread gets a queued reply without disrupting work; a closed thread has a clear pending state until a supported resume; a one-shot exec caller is explicitly unsupported for automatic wake.
  3. Cross-thread answers, duplicate events, lost queue responses, bridge restarts, session end/expiry and host-version mismatch have explicit outcomes. No duplicate business action is inferred to be safe merely because prompt delivery was deduplicated.
  4. Credentials and feedback never enter process arguments; the answer read returns the exact frozen proposal and answer. Agent acknowledgement remains distinct from queued receipt.
  5. Measure idle-answer-to-turn-start time, tool calls and tokens spent waiting, install effort and reconnection behavior against the current held-read path. Keep existing waiting-agent latency separate from next-turn scheduling latency.

If that succeeds, amend the Blueprint with automatic delivery as the supported-client experience, installation/setup requirements, lifecycle/error states and evidence requirements. Explicitly decide whether exited-process resume is included or remains queued until the user resumes. Decide on a multi-session subscription and E2EE only after their distinct value is established.

Plannotator Inbox delivery: source notes

Researched 2026-10-27. Read-only source inspection at Plannotator commit a104c2068f23ec9cc95c5216ad4f679aa8c9bde2. No product installation, credentials, or live delivery test. “Verified” below means verified in this source snapshot, not measured against a running host.

Main finding

Verified: the apparent push experience comes from a process inside the agent harness that can submit a new user turn. For Claude Code, Pi and OpenCode 2, the network side is actually long polling below the model, with a held local HTTP request. The agent need not spend turns calling a waiting tool. Codex is different: the Inbox invokes codex queue itself. Browser updates use SSE; this is a separate channel from agent delivery.

Claude Code

  • Verified: a per-session InboxLink proxies tools to the local Inbox MCP endpoint, filling the actual session ID and project. A one-second timer manages idle state and a background bridge poll. The held poll asks for 20 seconds; failed connections back off from 5 to 60 seconds. Pending replies wait for two consecutive idle ticks. Connection description and constants, poll implementation.
  • Verified: ordinary delivery calls $.prompt.submit({ text }); explicit Send now can append a user message with $.session.append, so the next model request sees it during an existing turn. The adapter checks an append refusal. Actual host adapter, delivery implementation.
  • Documented host requirement: Plannotator plugin plus its mod, Claude Code 2.1.287 or later. Send now has a separate 2.1.301 floor in code. This is a hooks-module integration with live engine APIs, not merely an ordinary shell hook returning text. Inbox docs, append version gate.

Pi and OpenCode

  • Verified: both share InboxWake. It holds a 20-second local bridge request, runs a one-second management tick and delays ordinary delivery for two idle ticks. Leases choose the most recently used host process when two processes have the same session open; atomic claim directories coordinate individual replies. Shared connection, timing constants.
  • Verified: Pi extension calls pi.sendUserMessage(text, { deliverAs: "followUp" }); Send now uses "steer". It checks idle/pending-message state and whether a run settled. Delivery completes when Pi starts that user message, with a watchdog for failures. Wake setup requires an interactive UI; print/JSON runs do not have it. Pi integration, actual send and target, interactive activation.
  • Verified: OpenCode 2 plugin calls session.prompt with delivery: "queue", or "steer" for Send now. It uses runtime events plus bounded idle probes; older OpenCode has the tool but no wake. Runtime distinction, actual prompt calls.

Codex

  • Verified: there is no Plannotator Codex plugin. The stdio MCP shim learns the thread ID from tool-call metadata; the server checks a queue-capable Codex CLI. Persistent sessions qualify, while codex exec is excluded. Minimum version is 0.149.0 in Plannotator's code. Core contract, server description.
  • Verified: it executes the CLI directly with an argv array: codex queue --thread=<id> --message=<text>. No terminal typing or shell interpolation. This does expose reply text transiently in the process list. Actual execution and results.
  • Documented upstream behavior, not independently exercised: idle threads run the queued turn quickly; busy threads take it next; closed threads take it on resume. Source comments also mention a background-server headless case. Treat those timing/lifecycle claims as Plannotator's compatibility assumptions until tested against our supported Codex versions.
  • Verified: exit 0 means queued, not delivered. Later tool metadata or explicit reads establish delivery. It persists a per-item/thread claim before invoking the CLI. A timeout is ambiguous and is never automatically resubmitted; the reply remains available to read. This favors avoiding duplicate turns over guaranteeing delivery. Unknown threads become ended; other CLI failures retry. State semantics, result handling.
  • Verified: this dispatch is triggered by store events and selected retry/start/resume events, not a model polling loop. A concurrent wait_for_reply suppresses queueing that reply. Sweep.

Shared relay and fallback

  • Verified: /api/inbox/bridge/poll returns immediately if pending data exists; otherwise it subscribes to store events and holds the request until a message, abort or timer. The server caps this at 25 seconds. It is event-woken long polling rather than periodically querying storage while held. Server implementation.
  • Verified: unsupported clients call wait_for_reply. Its 50-second default is another store-event subscription with a timer; timeout returns a cursor. Thus they retain a model/tool wait loop. Default, wait implementation.
  • Verified: the user-facing browser listens to SSE with EventSource, preserving an event cursor on reconnect. This does not by itself wake an agent. Browser event client.
  • Verified: feedback becomes formatted prompt text with a subject, message ID, fixed provenance/instruction line, verbatim body, and thread/tool pointers. It is not a distinct model-native decision channel. Formatting implementation.

Trust and security boundary

  • Verified: normal Inbox binds loopback. Bridge/control endpoints require the correct loopback Host, no Origin, and a bearer token; token storage is an owner-only registry file. Browser writes use origin checks and a server-session nonce. Server boundary, route enforcement, registry permissions.
  • Verified limitation: local MCP has no authentication token; it rejects browser Origins and remote Hosts. Consequently the design trusts local non-browser processes, and its shared registry token is not per-agent isolation. Same-user untrusted code is not contained by this design. MCP route.
  • Documented remote boundary: supported Tailscale publishing goes through a separate owner-identity-checked listener, with agent routes kept local. This replaces AgentPager's public cloud relay with tailnet membership and local-machine availability. Source also contains a separate feature-gated phone surface, so “no mobile functionality” would be too broad. Listener overview, remote access docs.

Implication for AgentPager (inference)

The transferable idea is a trusted local companion that holds the transport open and binds each answer to a real harness session, then uses a supported queue/follow-up API to wake it. Choosing WebSocket or SSE instead of long polling is secondary. A compiled Bun binary can house that companion, broker secrets outside model context, validate envelopes and manage a durable outbox, but cannot create a wake API in a host that lacks one. Extensions provide that host-specific capability for Pi/Claude/OpenCode; Codex may need only its existing queue CLI. These are architectural inferences, not implemented AgentPager changes or a complete security audit.
