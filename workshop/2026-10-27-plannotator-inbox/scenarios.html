What does each extra install buy the user?

MCP makes AgentPager easier to call. A local bridge adds automatic continuation when the owner answers after the agent has gone idle.

Four scenarios using the same relay and phone flow. Diagrams show logical machine/service boundaries and numbered decision flow. They are proposed architecture comparisons, not a running integration.

1

Scenario

Terminal + HTTPS

Lowest setup effort

You answer on your phone while the terminal agent holds an answer read open. It continues when that read returns.

Current contract

User install steps

  • Install Codex CLI
  • Give agent AgentPager /start URL
  • Open pairing link on iPhone

+ Pros

  • No AgentPager software to install on the agent machine.
  • Phone can answer from anywhere with Internet access.
  • A waiting caller receives the answer promptly; a persistent shell wait can avoid repeated model turns.

− Cons / risks

  • If the agent stops waiting, your answer stays stored until another read. No idle-session wake-up.
  • Closing the terminal or sleeping the machine can stop progress.
  • Session keys may enter model context, shell commands or transcripts; HTTPS does not hide content from the relay.

Protocol and behavior

  1. Agent uses its shell to POST a question to AgentPager over HTTPS.
  2. Agent/caller holds GET answer?wait=… open for up to 50 seconds; repeats if pending.
  3. iPhone reads cards over HTTPS (polls every 3 seconds today), then POSTs the owner’s frozen answer after Send/Undo.
  4. The held read returns the answer. Agent decides next work and sends an acknowledgement over HTTPS.

Product investment → user return: Maintain the existing API and /start instructions. Good entry path and lowest distribution burden; it leaves continuation dependent on an active caller.

2

Scenario

Desktop + remote MCP

Easier tool use; same waiting behavior

You add AgentPager once as a tool server in Codex desktop. The agent asks and waits through tools, while your phone uses the same relay.

Current contract + client qualification

User install steps

  • Install Codex desktop app
  • Add AgentPager remote MCP server
  • Open pairing link on iPhone

+ Pros

  • One-time tool setup replaces handwritten HTTP requests.
  • Fits the desktop assistant workflow; no separate AgentPager binary.
  • The same MCP connection can also serve Codex CLI—desktop is not required for this tier.

− Cons / risks

  • Adding this remote MCP server alone does not start a new turn when the agent is idle.
  • A waiting tool can time out; the caller must continue or resume the wait.
  • AgentPager session keys remain tool arguments in the current design. This is not a stronger confidentiality boundary than HTTPS.

Protocol and behavior

  1. Codex calls ask_card on the remote AgentPager MCP server. MCP messages travel over HTTPS (Streamable HTTP).
  2. Codex calls wait_for_card_answer. A pending result requires another wait call.
  3. iPhone reads the card and POSTs the answer over HTTPS; it does not connect to the MCP client.
  4. The waiting tool returns the answer into the current run. The agent calls acknowledge_card.

Product investment → user return: Package clear MCP onboarding and qualify desktop behavior. Useful setup ROI, but no automatic-continuation ROI by itself.

3a

Scenario

Local binary + terminal

Automatic continuation in the same session

The agent posts a question and can continue other work or go idle. The helper receives your answer and queues it into that exact Codex session.

Proposed · recommended first proof

User install steps

  • Install/update Codex CLI
  • Install AgentPager helper
  • Add helper as local MCP server
  • Open pairing link on iPhone

+ Pros

  • You can answer after the agent has gone idle; the helper can trigger its next turn.
  • Agent stays free to do independent work instead of maintaining a waiting tool call.
  • Helper can own relay keys outside model arguments and avoid inbound network ports on your computer.

− Cons / risks

  • You install and trust local code capable of prompting your coding agent. It needs updates and compatible Codex versions.
  • Helper/runtime must stay alive and machine online. A closed runtime may need manual resume; this is not a machine wake service.
  • Misrouted or duplicated answers could trigger wrong work. Exact thread binding, deduplication and honest queued/ack states are required.

Protocol and behavior

  1. Codex posts the card through local MCP over stdio (child-process stdin/stdout, no network listener). The post tool returns immediately.
  2. Helper POSTs to AgentPager over HTTPS and maintains the held answer read outside the model. Use the existing API first.
  3. Owner sends on iPhone; relay stores the answer and completes the helper’s read.
  4. Helper invokes local codex queue for the originating thread, ideally with an opaque answer reference. Busy runtime queues; idle runtime can start the next turn.
  5. Agent retrieves the exact frozen answer via a local tool and explicitly acknowledges it. The helper relays that acknowledgement.

Product investment → user return: Build one helper executable, exact thread binding, delivery state and lifecycle qualification. This is the first layer that directly reduces “I answered, but the agent stayed stopped.”

3b

Scenario

Local binary + desktop

Same continuation benefit in the desktop UI

The local helper serves the desktop app through MCP and uses the Codex wake adapter for its originating thread. The owner’s phone flow is unchanged.

Proposed · same bridge, second client surface

User install steps

  • Install Codex desktop app
  • Install AgentPager helper
  • Ensure compatible Codex queue is available
  • Add helper as local MCP server
  • Open pairing link on iPhone

+ Pros

  • Same automatic continuation, with the desktop conversation and review UI.
  • Shares relay, credential handling and delivery code with the terminal scenario.
  • No separate custom desktop plugin is inherently required for the researched Codex queue approach.

− Cons / risks

  • Desktop/backend/thread compatibility must be proved; shared settings alone do not establish that queueing targets the right running thread.
  • Setup must locate a compatible bundled or installed Codex CLI. If it cannot, report unsupported rather than claim wake-up works.
  • App close, backend shutdown, sleep and permission prompts can still block progress. Installed helper has the same prompt-injection authority as 3a.

Protocol and behavior

  1. Desktop app calls the helper’s local MCP tools over stdio. It binds the true Codex thread, not a conversation title.
  2. Helper exchanges cards/answers with the same AgentPager cloud API over outbound HTTPS. iPhone uses that API too.
  3. When the answer arrives, helper invokes codex queue for that desktop thread. This depends on a qualified backend/store/version combination.
  4. Desktop Codex consumes the queued input, reads the answer and sends its own acknowledgement through the helper.

Product investment → user return: Reuse the helper and qualify the desktop environment: binary discovery, thread identity, backend lifecycle and UI receipts. Same network architecture; separate compatibility and onboarding work.

Recommendation

Invest in the continuation layer first.

Prove 3a, then qualify 3b against the same helper. Keep 1 and 2 for users who want less installation. MCP onboarding is useful, but moving from terminal to desktop does not have to precede adding the helper.

Effort and return are qualitative judgments, not measured adoption, token, latency or revenue results. Start with existing HTTPS held reads inside the helper. No new cloud streaming endpoint is needed to prove the main behavior.

The reliability floor stays the same.

Awake host versus exited process

“Wake the agent” here means submit another turn to a supported runtime on an awake, connected machine. An exited runtime may keep the reply queued until resume. Restarting the process needs a separate launcher/supervisor policy. A sleeping or offline laptop cannot execute work.

Where the helper belongs

All diagrams assume Codex and helper share one machine. For a terminal agent on a cloud VM, replace the agent-machine column with that VM and install the helper there. A helper on your laptop does not automatically control a different machine’s Codex thread.

Stored, queued, read, done

These are separate states. Server receipt means stored. Queue success means accepted for delivery. Only the agent’s acknowledgement confirms it read the answer; even that does not prove it completed the work.

Security does not follow install count

Every shown HTTPS hop is encrypted in transit; the relay can still read plaintext. A helper can keep relay keys out of model arguments, but unrestricted same-user code may still reach them. No scenario shown includes proven E2EE or immunity to a compromised host.

Native notifications add another service: a future iPhone notification path would be AgentPager → Apple APNs → iPhone. It is a notification path, separate from the HTTPS card/answer exchange shown above. The native app, push service and its detailed privacy design are outside these four scenarios.

What to prove before promising 3a or 3b

  1. Post a card, finish the current agent turn, answer on iPhone, and observe the exact session start another turn.
  2. Repeat while busy, after helper restart, with a duplicate answer event and after session expiry. No answer may cross into another thread.
  3. Close the terminal/app and distinguish pending-until-resume from actual process restart. Do not label either as “agent received it” early.
  4. Keep credentials and feedback out of process arguments. Queue an opaque reference; retrieve the bound answer through a local tool.
  5. Run separately in CLI and desktop; verify Codex binary version, thread metadata and backend store. The desktop wake path remains unproved here.
